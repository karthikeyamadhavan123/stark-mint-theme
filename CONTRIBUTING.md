# Contributing to Stark Mint

Thank you for your interest in contributing to Stark Mint!

Stark Mint is an open-source desktop theme inspired by Iron Man Mark III and Stark Industries. The project welcomes contributions that improve its quality, usability, compatibility and completeness.

Our goal is to build a cohesive desktop experience while preserving the project's visual identity.

## 1. Before Contributing

Before submitting a contribution, please read:

- [README.md](README.md) — Project overview and installation.
- [DESIGN.md](DESIGN.md) — Visual identity and design principles.
- [CREDITS.md](CREDITS.md) — Upstream attribution and licensing information.

All visual contributions should follow the guidelines in `DESIGN.md`.

## 2. Areas Where Contributions Are Welcome

Contributions are welcome in the following areas:

### Visual improvements
- GTK 3 and GTK 4 styling.
- Cinnamon desktop styling.
- Window decorations and controls.
- Icon design and icon coverage.
- Cursor integration.
- Wallpaper and preview assets.

### Technical improvements
- Bug fixes.
- Accessibility and contrast improvements.
- Desktop-version compatibility.
- Installer and uninstaller reliability.
- Packaging and installation improvements.
- CSS and configuration cleanup.

### Project improvements
- Documentation.
- Installation guides.
- Screenshots.
- Testing and bug reports.
- Compatibility reports.

## 3. Design Requirements

All visual contributions must respect `DESIGN.md`.

In particular:

- Graphite and charcoal must remain the neutral foundation.
- Stark Red and Metallic Gold are the only theme accent families.
- Gold represents interaction and active states.
- Red represents identity, errors and destructive actions.
- Cyan, turquoise, teal, blue, green and purple must not be introduced as competing theme accents.
- Readability and usability must not be sacrificed for appearance.
- Third-party application icons should retain their recognisability.

Changes to the core palette or overall design identity require explicit maintainer approval.

## 4. Reporting Bugs

If you discover a bug, please open a GitHub Issue.

Include as much of the following information as possible:

- Linux distribution and version.
- Desktop environment and version.
- GTK version, if relevant.
- Affected theme component.
- Steps to reproduce the issue.
- Expected behaviour.
- Actual behaviour.
- Screenshots, if the issue is visual.

Please check existing issues before creating a duplicate report.

## 5. Suggesting Improvements

Ideas and suggestions are welcome.

When proposing an improvement, explain:

1. What problem are you trying to solve?
2. Which component is affected?
3. How would the change improve usability, consistency or appearance?
4. Does the proposal follow the Stark Mint design principles?

Suggestions involving changes to the core design identity require maintainer approval.

Not every suggestion will necessarily be implemented, but constructive feedback is appreciated.

## 6. Making Changes

For code and theme contributions, the recommended workflow is:

1. Fork the Stark Mint repository.
2. Clone your fork locally.
3. Create a separate branch for your change.
4. Make your changes.
5. Test the affected component.
6. Commit your changes with a clear message.
7. Push the branch to your fork.
8. Open a Pull Request against the main Stark Mint repository.

Keep contributions focused. Avoid combining unrelated modifications in one Pull Request.

## 7. Testing Requirements

Please test changes in the relevant desktop environment before submitting them.

For visual changes:

- Include before-and-after screenshots where useful.
- Identify the desktop environment and version.
- Mention which GTK or Cinnamon components were tested.
- Check normal, hover, focus and active states where applicable.
- Check that text and controls remain readable.

Do not claim compatibility with desktop versions that you have not tested.

## 8. Licensing and Attribution

Contributors must:

- Submit work they have the right to distribute.
- Preserve existing copyright notices.
- Preserve upstream licence notices.
- Identify third-party assets and their licences.
- Avoid submitting assets with unclear redistribution rights.

By submitting a contribution, you agree that it may be distributed under the applicable licence or licences of the files being modified.

If you are unsure about the licensing of an asset, discuss it before submitting it.

## 9. Pull Request Guidelines

Every Pull Request should include:

- A clear description of the change.
- The reason for the change.
- The affected files or components.
- Testing performed.
- Screenshots for visual changes.
- Any known limitations.

The maintainer will review contributions for technical correctness, compatibility, licensing and consistency with `DESIGN.md`.

A Pull Request may be revised or declined if it conflicts with the project's direction.

## 10. Project Direction

Stark Mint is intended to improve through community participation.

The project welcomes new ideas, technical improvements and constructive criticism.

However, community contributions should improve the execution rather than redefine the identity.

**Improve the execution. Preserve the identity.**

Thank you for helping make Stark Mint better!
